1The user: Noor, support agent at an Iraqi mobile-wallet company, Baghdad

Noor works the support queue. Tickets arrive from in-app chat, WhatsApp and Telegram, almost all in Iraqi dialect, often mixed with English (الـ OTP ما وصل) or written in Arabizi (ma wasal el mablagh). She handles a full queue every shift (we will measure the real volume in interviews). For every ticket she repeats the same loop:

1 · Reada paragraph of dialect
2 · Work out the issuetransfer? login? agent?
3 · Dig out the factsref, amount, date
4 · Judge urgencyand pick a team
5 · Route or replyoften the same text again

The problem

  • Repetition. Most of the queue is a handful of issues and "how do I…" questions, answered the same way every day. The queue grows faster than the team.
  • Wrong order. The queue is first-come, first-served. A 5,000,000 IQD transfer to the wrong number, still reversible for a few hours, waits behind a PIN reset.
  • Facts buried in text. Refs, amounts written in words (مليون ونص) and relative dates (امس بالليل) have to be found by hand before anything can be looked up.
  • No overview. Haider, the team lead (secondary user), cannot see what came in, what is stuck, or what is suddenly spiking.

Not the user: the customer. This is not a chatbot. The customer only ever receives text that a human approved.

2What a good day looks like for Noor

  • Her queue is already sorted by a priority score she can read (why this ticket is P1)
  • Routine tickets arrive with a draft she sends after a minor edit
  • Hard tickets arrive marked Needs you with a one-line reason
  • A customer who asks for a person always reaches one
  • Nothing reaches a customer without her click, at any confidence
  • Haider gets a run report: volume, routing, escalations and why

3A workflow, not an autonomous agent

The steps are known in advance (classify → extract → prioritise → route → draft). Following Anthropic's Building effective agents, we use a fixed workflow (prompt chaining + routing), not an open-ended agent. The LLM handles language; code makes the decisions. This makes it easier to test, debug and trust.

4Checking the problem with real people

In week 1 we interview 2–3 people who do support in Iraq (wallet, telecom, e-commerce) for 20 minutes each. We ask about their category list, the most repetitive tickets, how they judge urgency, and how often customers ask for a human. Findings go in docs/USER_RESEARCH.md and adjust the categories and priority weights below.

DESIGN BRIEF · 2 / 5 · HOW IT WORKS

End to end: six steps, two LLM calls, one human gate

A batch pipeline, not a chatbot
Runs over a queue of tickets and writes a run report

④Decision rules: first match wins

1Customer asks for a human (LLM flag OR phrase list: اريد موظف، مو روبوت) → Needs you, no AI draft
2Suspected prompt injection → Needs you, draft suppressed
3Fraud, account takeover, legal threat → Needs you "sensitive"
4Confidence < τ, the two models disagree, LLM error, two issues in one ticket, P1 with no ref, Kurdish → Needs you + reason
5Otherwise → team from routing.yaml, ⑤ prepares a draft

③Priority score: readable, not the model's opinion

The LLM extracts facts; code adds the points:
category 5–35 · amount (≥250k +10, ≥1M +20, ≥5M +30) · money stuck (>24h +10, >72h +15) · still reversible (wrong recipient <24h) +15 · fraud +40 · repeat contact +10 · asked for human +10 · +1 per hour waiting (max 15).
≥ 60 P1 · 35–59 P2 · < 35 P3. The breakdown is shown on every ticket.

llm.py: one OpenAI-compatible function, so switching provider changes only the base URL and key. Responses are cached on disk by (prompt version + input hash), so re-runs are free and repeatable. A 429 error → exponential backoff → the next provider. Keys live in a git-ignored .env. Anthropic has no free API tier, so Claude is used only as the coding assistant (Claude Code), and that is disclosed.

2Tools

Python 3.12 · Pydantic (output schemas) · Typer (CLI: run / eval / admin) · SQLite (queue + audit log) · Streamlit (admin page, Arabic RTL) · CAMeL Tools (Arabic normalisation) · rank-bm25 · Faker · promptfoo (compare prompts and models on dev) · pytest + GitHub Actions · gitleaks (no keys in the repo).

3Synthetic data: code writes the facts, the LLM writes the words

1
Spec. Category list, 6 personas (student, shop owner, older user typing via a relative, angry repeat customer, office worker, rural cash-out customer), 3 channels, a list of noise types, and a dialect style guide (data/STYLE_GUIDE.md).
2
Facts by code, before any text. Python + Faker pick the ground truth: category, amount (IQD/USD), ref, date, 07xx number (075/077/078/079), agent, which fields are missing, flags, priority. Labels are exact by construction.
3
LLM writes the ticket. Mistral turns each fact sheet into a customer message in Iraqi dialect with the requested noise: typos, Arabizi, English mixed in, amounts in words (مليون ونص), missing details, anger, two issues at once.
4
Automatic checks. Every non-missing fact must appear in the text (parsed back), dialect markers present (not pure MSA), no near-duplicates, sensible length. A failure → regenerate.
5
Human QA. I read every 5th ticket and rewrite anything that sounds translated. A second native speaker rates 40 tickets for realism (1–5); the scores are published.
6
Split and freeze. 400 generated → ≥ 300 kept → dev 50% · test 25% · held-out 25%. Hashes are committed; generator seed and prompts are saved so the data can be reproduced.

Planned mix: all 10 categories · ~30 "I want a human" · ~50 how-to (10 the manual can't answer) · ~30 injection attempts · ≥ 15% edge cases (no details, MSA / English / Kurdish). Plus a synthetic 25-article app manual.

1How we measure

  • eval.py, one command: runs the pipeline on a split, compares against the labels, and writes docs/EVALUATION.md (tables, confusion matrix, calibration plot)
  • promptfoo compares prompt versions and models, on dev only
  • Human ratings: raters see the ticket and the draft, never the model or its confidence; we report how often raters agree
  • Unit tests for every rule, the priority formula, the validator and the "no send path" check

2Robustness checks

  • New tickets written by hand, as judges will do
  • 429 errors, timeouts and broken JSON injected mid-batch: the batch must still finish
  • A 500-ticket run; the same input gives the same output (cache)

3Confusion cases we will write up

failed transfer ↔ wrong recipient (both "the money didn't arrive") · login ↔ OTP · how-to ↔ fee question · رصيد = wallet balance or phone credit. Each comes with examples and what would have resolved it.

4Rules we hold ourselves to

  • Never tune on test or held-out; held-out is opened once
  • Failures are listed with ticket IDs, not hidden
  • Results stay honest about being on synthetic data only

1Main risks and what we do about them

RiskHandling
Free-tier limits or provider outage mid-run or mid-demoCache, backoff, provider chain Groq → Gemini → Ollama. The demo uses a cached batch plus a few live tickets. Organisers told early if needed
Confident but wrong (dialect ambiguity, e.g. رصيد)τ tuned on dev; second-model agreement on borderline tickets; a human approves every reply anyway
Prompt injection (OWASP LLM01)Scanner; ticket wrapped in random-nonce data tags; LLM has no tools and cannot send; output validator + canary token; 30-ticket red-team set
Invented ref, amount or manual stepEvery number in a draft must be in the extracted facts; manual answers must cite a real section. Otherwise → Needs you
Missed "talk to a human"Two detectors, OR-ed and tuned for recall. The ticket still reaches a person before any reply
Synthetic tickets too clean or sound translatedFacts-first generator with deliberate noise, native-speaker QA, interview phrasing. "Synthetic only" stated as a limitation
Priority weights wrong in edge casesFraud always lands in P1; agents' re-prioritisations are logged; weights live in YAML
Free tiers may train on prompts; keys could leakSynthetic data only; .env is git-ignored; gitleaks runs in CI
Too much scope for 2.5 weeksMVP is CLI + CSV/SQLite queue. Web page, second model and weekly report come after the MVP
